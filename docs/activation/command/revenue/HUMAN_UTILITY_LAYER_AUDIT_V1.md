# Human Utility Layer Audit v1

**Scope:** Public-language and onboarding analysis only.  
**Boundary:** No protocol feature, contract, wallet, minting, liquidity, staking,
governance, or financial action is proposed or authorized here.

## Core finding

QPF currently proves technical reality well: public deployment evidence,
reproducible checks, technical documentation, local-AI direction, and a
services path. It does not yet present a simple, current consumer product.

Public messaging must therefore distinguish:

1. **What can be verified or purchased today.**
2. **What is an intended future capability.**
3. **What is explicitly not active.**

## Three entry paths

### 1. Individual: Learn and verify

**Question:** "What is this, and can I inspect it without financial exposure?"  
**Current route:** Home → What It Does / Why This Matters → Deployed Addresses.  
**Existing support:** Plain-language pages, public evidence, explicit inactive
economics, and no-wallet-required verification.  
**Gap:** No packaged individual utility or guided non-technical verification
experience exists yet.

### 2. Developer: Build or verify

**Question:** "Can I reproduce this, integrate with it, or contribute safely?"  
**Current route:** Home → For Builders → GitHub / deployed addresses.  
**Existing support:** Builder documentation, source repository, public deployment
records, and reproducible verification material.  
**Gap:** The first contribution and first verification task should be shorter and
more prominent.

### 3. Business: Request an evidence-first engagement

**Question:** "Can QPF help us prove what is real, prepare diligence, or improve
technical trust?"  
**Current route:** Home → Work With Quantum Pi Forge → Project brief email.  
**Existing support:** Service descriptions, project-brief CTA, discovery and
proposal templates, and an evidence-readiness first milestone.  
**Gap:** Publish a concise FAQ and one anonymized example only when supported by
real client or internal evidence.

## Language changes with highest expected impact

| Priority | Change | Rationale |
| ---: | --- | --- |
| 1 | Add a visible audience choice: "Verify a project", "Build with QPF", or "Improve technical trust". | Routes visitors by goal before technical vocabulary appears. |
| 2 | Lead business pages with the problem and first milestone, not infrastructure terms. | Makes the paid path understandable to non-crypto teams. |
| 3 | Keep protocol-economics status visible but secondary to the human outcome. | Preserves safety truth without making inactive features the primary story. |
| 4 | Add a short FAQ covering scope, inputs, deliverables, and what QPF does not do. | Removes common engagement objections without inventing pricing or claims. |

## Recommended next change

Add a three-path audience selector to the public homepage using only existing
destinations:

- **Verify a project** → `deployed-addresses.html`
- **Build or contribute** → `for-builders.html`
- **Improve technical trust** → `work-with-us.html`

This is a language and navigation improvement only. It does not create a new
protocol capability or make a commercial claim beyond the current services path.
