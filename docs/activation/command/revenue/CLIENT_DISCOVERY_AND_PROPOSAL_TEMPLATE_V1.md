# Client Discovery and Proposal Template v1

**Purpose:** Turn a public website inquiry into a clear, evidence-first services
proposal. This is for commercial services only; it does not authorize protocol
economics, wallet operations, or financial transactions.

| Fit decision | `pending` |

## 2. Fit screen

Proceed only when all applicable answers are clear:

- Is the request for a service QPF can evidence or deliver?
- Is the requested outcome lawful, non-custodial, and outside protocol activation?
- Can a first milestone be stated with a concrete output and acceptance check?
- Are required client inputs identified without requesting secrets or private keys?

Decline or redirect requests for token issuance, liquidity, staking, custody,
signing, transfers, governance control, or any action requiring a client secret.

```text
Title:

Client inputs:
Acceptance checks:
Timeline:
Assumptions and exclusions:
Price and payment terms: TBD_HUMAN
Next decision:
```

For evidence-readiness work, the default first milestone can be:

1. Claim-to-evidence map.
2. Reproducible verification results.
3. Risk and missing-evidence list.
4. Prioritized next-action brief.

## 4. Handoff record

Record only non-sensitive operational facts:

- Proposal sent date.
- Client response state: `open`, `declined`, `proposal_sent`, `engaged`, or
  `closed_lost`.
- Stated conversion blocker, if any.
- Next follow-up date.

Do not record credentials, private keys, payment-card data, or transaction
instructions in the repository.
