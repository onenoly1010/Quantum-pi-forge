# Quantum Pi Forge Site Reviewer Onboarding

## 1. Architectural Posture: What the Interface Is

The Quantum Pi Forge interface is not a speculative Web3 landing page, marketing funnel, or token-generation hype surface. It is a functional, high-fidelity operational review dashboard for the OINIO Soul System and its decentralized AI infrastructure.

The terminal-style aesthetic is a deliberate design choice reflecting the platform's core values: deterministic truth, cryptographic verification, and local data sovereignty. The density of the interface is intentional, serving operators who require direct, unvarnished telemetry over polished corporate narratives.

---

## 2. Functional Delivery: What Is Live Now

Reviewers can interact with and verify several core components immediately:

- **0G Aristotle Mainnet telemetry:** Live-facing telemetry from the mainnet layer, providing a review surface for network and ledger integration rather than a purely simulated dashboard.
- **Local AI activation path:** Functional command-line onboarding tracks that allow users to pull local sovereign models, such as `qwen2.5-coder`, through Ollama, demonstrating edge-execution capability.
- **Open verification materials:** Direct public links to guardian scripts, repository manifests, and review materials, establishing a trust signal through structural transparency.
- **State-transition visibility:** Monitoring fields that expose system state through concepts such as `Resonance Oracle` and `Guardian Consensus`.

---

## 3. Cryptographic Integrity: What Is Intentionally Disabled

Certain execution surfaces, including specific staking portals, relayer execution protocols, and advanced contract interactions, are explicitly marked as disabled or locked.

- **Integrity over representation:** These features are restricted pending finalized bytecode verification, contract freezes, or security clearance.
- **The posture:** In an ecosystem built around no admin backdoors and bounded authority, disabling an unverified surface is a demonstration of strict security posture, not an architecture failure. Features are only exposed when they can be represented truthfully.

---

## 4. Evaluation Framework: How to Review the Site

To accurately assess the platform, a first-time reviewer should distinguish between four distinct operational zones:

1. **The public interface:** The immediate operational dashboard tracking network-wide metrics and live-facing synchronization.
2. **The local execution path:** The hardware-first onboarding steps that transition the user from observer to local operator.
3. **The verification evidence:** The underlying repositories, guardian scripts, manifests, and smart contract evidence available for independent auditing.
4. **The future-facing modules:** Features explicitly locked down to prevent speculative interaction before full deployment and security clearance.

---

## 5. Architectural Mandate: Why Local AI Matters

The inclusion of localized hardware commands, including Ollama-based model activation, serves as a proof path for cloud independence.

By guiding the reviewer to run models locally, the platform demonstrates that the OINIO Soul System does not need to depend exclusively on centralized, gatekept LLM provider APIs. It shows that sovereign AI workflows can be provisioned, executed, and validated on user-owned hardware, supporting local data control and reducing dependency on centralized inference providers.
